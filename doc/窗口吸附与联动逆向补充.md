# TTPlayer v5.7.9 窗口吸附与联动逆向补充

> 目的：针对“原版为什么多窗口拖动非常流畅，而当前复刻版拖动发卡”的问题，单独整理原版窗口吸附、拖动、多窗口联动的逆向结论，并给出可落地的复刻方案。  
> 范围：仅关注窗口移动、吸附、联动，不覆盖皮肤、播放、歌词等其他模块。

---

## 1. 结论摘要

原版 TTPlayer 的窗口吸附和联动并不是基于轮询，而是典型的 Win32 消息驱动模型：

- 鼠标按下后通过 `SetCapture` 进入拖动会话。
- 在拖动消息里计算主窗口或某个子窗口的位移增量。
- 先确定这次拖动要联动的窗口集合。
- 使用 `BeginDeferWindowPos -> DeferWindowPos -> EndDeferWindowPos` 一次性批量提交所有窗口的新位置。

这套模型流畅的根本原因不是“算法更复杂”，而是：

- 联动集合在一次拖动过程中是稳定的。
- 所有窗口位置在一帧内一起提交，不会出现逐个 `move()` 的波浪式更新。
- 状态集中保存在拖动会话对象里，而不是依赖运行时反复重算。

当前复刻版发卡的主要原因不是吸附判定本身，而是“逐窗移动 + Qt/XWayland 窗口系统往返 + 联动集合动态变化”叠加导致的。

## 2. 原版配置证据

原版配置文件里明确存在吸附参数：

```xml
<General
    Fade_Windows="0"
    Snap_Windows="65546"
    TitleSlideInterval="65541"
/>
```

文件：`TTPlayerv5.7.9/TTPlayer.xml`

观察点：

- `Snap_Windows="65546"` 不是一个简单布尔值，更像“位标志 + 数值”的混合编码。
- `65546 = 0x1000A`，低 16 位是 `0x000A = 10`，很像阈值；高位 `0x10000` 更像启用位或模式位。
- 同文件中的 `TitleSlideInterval="65541"` 也呈现同类编码方式，说明这不是偶然。

推断：

- 原版窗口吸附阈值更可能是 10px 左右，而不是之前文档里推测的 20px。
- `Snap_Windows` 很可能同时编码“是否启用吸附”和“吸附距离阈值”。

## 3. 原版二进制证据

### 3.1 导入表确认原版使用的关键 Win32 API

通过 `objdump -p` / `winedump -j import` 可确认 `TTPlayer.exe` 导入了以下与窗口联动强相关的 API：

- `SetCapture`
- `ReleaseCapture`
- `GetMessagePos`
- `GetWindowRect`
- `MoveWindow`
- `SetWindowPos`
- `BeginDeferWindowPos`
- `DeferWindowPos`
- `EndDeferWindowPos`
- `SetTimer`
- `KillTimer`

这组 API 组合非常典型：

- `SetCapture/ReleaseCapture`：拖动会话控制
- `GetMessagePos/GetWindowRect`：基于消息位置算 delta
- `BeginDeferWindowPos/DeferWindowPos/EndDeferWindowPos`：批量移动一组顶级窗口
- `SetTimer/KillTimer`：可能用于拖动辅助、吸附提示、延时动画，不是主联动通路

重点是 `DeferWindowPos` 三件套。只要它真实出现在调用链里，基本就能说明原版不是“窗口一个个 move”。

### 3.2 `DeferWindowPos` 包装函数

在 `0x405352` 附近可以看到一个非常明显的包装调用：

```asm
405352:
  push [flags]
  push [cy]
  push [cx]
  push [y]
  push [x]
  push [insertAfter]
  push [hWnd]
  push [hdwp]
  call [DeferWindowPos]
```

这说明程序内部把 `DeferWindowPos` 包装成了一个统一的“加入批量移动队列”的函数。

### 3.3 明确存在“开始批量移动 -> 多次加入窗口 -> 结束提交”的链路

在 `0x419a75` 到 `0x419ae2` 一段可见完整流程：

```asm
419a75: call [BeginDeferWindowPos]
419a98: call [DeferWindowPos]
419aba: call 0x405352      ; 继续 DeferWindowPos
419adc: call 0x405352      ; 继续 DeferWindowPos
419ae2: call [EndDeferWindowPos]
```

这段非常关键，说明原版一次至少会批量提交 3 个窗口的位置变更，而不是逐个立即 `SetWindowPos`。

### 3.4 拖动会话使用了鼠标捕获

在 `0x419e10` 和 `0x419e26` 附近出现：

```asm
419e10: call [SetCapture]
419e26: call [ReleaseCapture]
```

说明原版在开始拖动时进入捕获状态，拖动结束时释放捕获。这是 Win32 下实现无边框流畅拖动的标准路径。

### 3.5 拖动过程中基于消息位置和窗口矩形计算 delta

在 `0x419e3e` 一段中可见：

- 从某个 32 位值里拆出 `x/y`
- 用 `GetWindowRect` 读取当前窗口矩形
- 计算 `deltaX/deltaY`
- 如果 `delta == 0` 则直接退出

这很像标准的：

1. 鼠标消息到来
2. 取消息坐标
3. 减去拖动起点或上次坐标
4. 得到本次 delta
5. 把 delta 作用到拖动链路上的所有窗口

### 3.6 另一条批量移动链路支持“间接吸附的多窗口一起走”

在 `0x4708ff` 到 `0x470995` 之间再次出现：

```asm
4708ff: call [BeginDeferWindowPos]
47092c: call [DeferWindowPos]
470952: call [GetWindowRect]   ; 取其他窗口矩形
470982: call [DeferWindowPos]  ; 继续加入另一个窗口
470995: call [EndDeferWindowPos]
```

而且这段里存在一个循环：

```asm
470936 ... 470990
```

说明原版不是只移动“主窗口 + 一个子窗口”，而是会遍历一个集合，把多个相关窗口都纳入同一批次提交。

这和“直接吸附 + 间接吸附”的联动模型是吻合的。

## 4. 原版状态机推断

结合配置、导入表和汇编，原版更像下面这套状态机。

### 4.1 拖动会话状态

拖动开始时建立一个短生命周期的上下文：

- `dragLeader`：当前被用户直接拖动的窗口
- `dragStartCursor`
- `dragStartRects[]`
- `moveGroup[]`：这次需要一起移动的窗口句柄集合
- `snapFlags`：来自 `Snap_Windows`
- `edgeMask / relationMask`：当前吸附边关系

要点：

- `moveGroup[]` 是在拖动开始时构建，或在吸附关系变化时重建。
- 一旦进入一次拖动，会尽量避免每个鼠标消息都重新从头扫描所有窗口关系。

### 4.2 吸附关系模型

原版大概率不是简单的 “bool snapped + offset”，而更像：

- 每个窗口节点维护一个“依附关系”
- 依附目标可以是主窗口，也可以是其他已吸附窗口
- 多窗口能形成一棵以主窗口为根的吸附树，或至少是一个无环有向图

因此：

- 主窗口移动时，整棵树跟着走
- 拖动树中的任意一个子节点时，也可能带动其祖先或同组节点联动
- 是否联动不取决于“是不是主窗口”，而取决于“是否属于当前拖动联动组”

### 4.3 批量位移提交

每次鼠标移动：

1. 计算 `deltaX/deltaY`
2. 调整 leader 的目标矩形
3. 根据吸附关系推导出其他窗口目标矩形
4. `BeginDeferWindowPos(count)`
5. 对 group 中每个窗口调用 `DeferWindowPos`
6. `EndDeferWindowPos`

这就是原版流畅的关键。

## 5. 为什么原版流畅

### 5.1 一次提交，多窗一起落位

原版不是：

- 主窗 `move`
- 等系统处理
- 子窗1 `move`
- 子窗2 `move`

而是：

- 所有目标矩形先算完
- 一次 `EndDeferWindowPos` 提交

这会显著减少：

- 重绘抖动
- 视觉上的先后错位
- 窗口管理器的中间态闪动

### 5.2 联动集合稳定

原版大概率在拖动期间冻结或半冻结联动组，而不是每次 `moveEvent` 都重新做一遍全局判定。

这样可以避免：

- 某帧 A 认为 B 属于同组
- 下一帧因为位置刚好跨阈值又把 B 踢出去
- 再下一帧又吸回来

这类抖动在现在的 Qt 版本里非常容易发生。

### 5.3 Win32 原生顶级窗口移动成本低

原版运行环境是 Win32。顶级窗口位置控制是原生能力，`SetWindowPos/DeferWindowPos` 是系统推荐路径。

而你现在的复刻版运行在：

- Qt Widgets
- XWayland / X11 / KWin
- 多个独立顶级窗口

这本身就比 Win32 多了一层平台抽象和窗口管理器交互成本。
